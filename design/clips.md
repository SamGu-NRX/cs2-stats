# Clips: how POV clips are rendered

Read by whoever changes the clip renderer (`app/src/clips`, `app/src-tauri/src/clips/`) or runs the first supervised render. It records which render path was chosen and why, what has been checked, and what has not. Issue #11.

## The decision

Clips record through **HLAE** (advancedfx), with a script that runs inside CS2 and drives the demo. The approach comes from CS2-povforge. CS2's own demo tools are the fallback if HLAE breaks after a game update.

I compared three paths on 2026-10-26, reading the two projects' source in reference clones (Chester-chs/CS2-povforge at 91be721, advancedfx/advancedfx at 9200981). Nothing was run against the game.

| | CS2-povforge | HLAE alone | CS2's built-in tools |
|---|---|---|---|
| What it is | A Python app: demoparser2 picks rounds, HLAE records, FFmpeg edits | The recording tool povforge uses: a loader that injects `AfxHookSource2.dll` into cs2.exe, `mirv_streams` recording, a JavaScript scripting API | `playdemo`, `demo_gototick`, `spec_player`, `startmovie` |
| Needs | Windows, Python 3.11, demoparser2, polars, HLAE, FFmpeg | Windows, HLAE, FFmpeg for video output | CS2 only |
| Licence | MIT | MIT | Valve's |
| Writes video | Through HLAE | Yes, an MP4 per take through FFmpeg, with a WAV of the game's sound | TGA frames and a WAV in the game folder; no output folder setting |
| Can find the player and the tick | Yes, through HLAE's script API | Yes: `mirv.getDemoTick()`, entities with `getSteamId()`, the observer target (`misc/mirv-script/src/types/mirv.d.ts`) | Commands only. A cfg cannot read the tick back, so timing is blind |
| Valve matchmaking demos | Named in its README | Plays what CS2 plays | Yes, while the demo matches the game build |
| HLTV demos | Named in its README | Plays what CS2 plays | Same build limit |
| Local demos (`tv_autorecord`) | Untested | Untested | Untested |

Why HLAE with a script:

- It is the only path that can check, inside the game, that the camera is on the right player before it records, and stop exactly at the end tick. A cfg with `mirv_cmd addAtTick` would fire at ticks without knowing where the camera is.
- It writes a finished MP4 per clip. `startmovie` writes raw frames into the game folder.
- povforge is an app, not a library, and its runtime is Python. This app's engine is TypeScript and its host is Rust, so the app copies povforge's approach (its `director.js` and its HLAE command) and credits it (THIRD_PARTY_NOTICES.md). Neither project is bundled.

Every path shares one limit. CS2 refuses a demo recorded on another game build ("Demo file is incompatible with this game version"), and an update can break HLAE until advancedfx ships a fix. advancedfx shipped CS2 fixes in 2.192.3 to 2.192.5 and in 2.192.8 (release notes, read 2026-10-26).

## How a render runs

1. The engine scores moments from facts (`app/src/stats/moments.ts`). A moment has its round, the POV player's SteamID64, and demo ticks with 5 s before the first kill and 3 s after the last (povforge's defaults), kept inside the round: no earlier than freeze end, and no later than the round's end unless a kill came after it. A clip also ends 0.5 s after the player's death when that comes first (`DEATH_TAIL_S`), so the death shows but the take stops before CS2's demo camera leaves the dead player, which the director would read as `camera_lost`. A kill the player's grenade makes after that is cut off, since their view cannot follow it. A won clutch runs from when the clutch began to the round's end. The reason's "round impact" adds up the win-probability credit from the player's kills in the round, so it can pass 100% when the round swings back and forth. The ranking points are ours, with no fit behind them.
2. The Clips page says which demo each moment needs. Only a Valve match has one: `<Steam library>\steamapps\common\Counter-Strike Global Offensive\game\csgo\replays\<demo>.dem`, named after the match's folder. Plugin recordings, converted logs and pro demos have none, and the page says so per match.
3. Choosing moments and pressing Render sends the host a typed request: each clip's id, its demo's file name, the POV player's SteamID64, its round and the ticks, and the HLAE.exe the user chose. The host (`app/src-tauri/src/clips/job.rs`) checks each demo is a regular file directly in CS2's replays folder, reached without a link, recomputes each clip's id from its demo, player and round and refuses a mismatch, so a request cannot file one moment's clip under another's id, refuses a tick range that runs past the end of the demo (its length comes from the demo's own file info, `CDemoFileInfo.playback_ticks`; the host cannot read the match's round ticks, which are in parquet) or starts before tick 2 s × tick rate + 1 (the director seeks 2 s ahead of a clip and must have the camera on the player before its start, and a demo plays from tick 1), and builds the job: HLAE's command from a fixed template, the director script and the plan. The dialog shows the plan, with HLAE's command written for PowerShell (`& 'HLAE.exe' '-noGui' ...`, each argument single-quoted so `&`, `%` and `$` in a path stay literal); it is not a cmd.exe command. The launch itself passes the arguments to the process and uses no shell. The plan carries a review value: a SHA-256 of everything a launch of it runs and writes, without the job's id and time (`job.rs review_hash`). A plan counts only for the request it was built for: when the HLAE path or the tools change, the dialog drops the old plan at once, and **Save** and **Launch** stay off until the new plan is built, and while a typed HLAE path waits to be checked. Nothing is written until **Save the plan only** or **Launch CS2 with -insecure**, which send the review value back; the host builds the job again under the guard and saves it, in a new folder named to the millisecond with a random suffix, only if the value matches. The director and the plan are written to temporary names first and renamed, the plan last, so a plan never exists without its director.
4. Launch (`clips_launch` in `clips/mod.rs`) builds the job again from the request saved in its plan.json, and refuses when the saved plan differs in anything (the command, a demo, a folder or a clip) or is not the plan the user reviewed: the dialog sends the review value again with the launch. It writes the director again from that build, so an edited director.js never runs. It runs under the clips guard (see Keeping operations apart). It first settles every earlier launch whose processes have exited, so their director lines are read before this session replaces `console.log`, and refuses while an earlier launch (settled or not, while its watcher runs) or any cs2.exe still runs. The command is always HLAE.exe with its hook beside it, this install's cs2.exe, and `-insecure -novid -condebug -console -sw -width 1920 -height 1080 +exec cs2stats_clips` as the game's command line. It draws a fresh 128-bit nonce from the system's random source and publishes the launch's record, `jobs\<job>\launches\<nonce>.json`: a sequence number one above the job's highest, and the take folders each clip already had. It writes this launch's copy of the director, with the nonce in it, as `launches\<nonce>.js`, and `game\csgo\cfg\cs2stats_clips.cfg`, whose one line loads that copy. If HLAE has no FFmpeg of its own, it writes `ffmpeg\ffmpeg.ini` beside HLAE.exe. Then it starts HLAE without waiting for it and publishes HLAE's process id and creation time as `launches\<nonce>.pids.json`, still under the same guard. If a step before HLAE starts fails (finding FFmpeg, the cfg, the start itself), the launch's result says at once that HLAE was not started, with the error. Once HLAE runs, the launch keeps it: if its process id cannot be published, the launch is recorded as damaged with the reason, so none of its takes counts, and the app still keeps the clips folder's OS lock and hands HLAE's process handle to the launch's watcher (see Keeping operations apart).
5. The director (`app/src/clips/director.template.js`) waits for the menu, sets up `mirv_streams`, and hides the demo bar by setting `demo_ui_mode` to 0 through HLAE's cvar API, keeping the value it found. It then plays each demo in turn. For each clip it seeks 2 s early, finds the player's controller by SteamID64, holds the camera on it by sending `spec_player <controller entity index>` every frame, and asks for first person until the observer mode reads in-eye (see Locking the camera). It records only when the camera was confirmed on that player in observer mode 2 (in-eye) on a frame before the start tick. Otherwise it seeks back and tries again, twice, then skips the clip with `why=camera_late`; it never starts late. It skips with `why=camera_mode_unknown` when HLAE cannot report the observer mode (the pawn's `getObserverMode`, since HLAE 2.171.0), and with `why=no_player` when the player is not in the demo. It records from the start tick to the end tick, stops with `why=camera_lost` if the camera leaves the player or first person, and finally puts `demo_ui_mode` back to the value it found and quits CS2. On an HLAE without the cvar API (before 2.187.4) it leaves `demo_ui_mode` alone, and the bar shows in the clips. Each line it logs starts with `[cs2stats]`, carries the launch's nonce, and lands in `game\csgo\console.log` (`-condebug`).
6. Back in the app, the page finds the takes. While a launch's HLAE or CS2 still runs, it says "Waiting for CS2 to close", holds Render, and checks again every 5 s (our interval, not measured) until they have exited and the launch is settled. HLAE records each clip into a new numbered folder, `%APPDATA%\BotMatchStats\clips\jobs\<job>\raw\<clip id>\takeNNNN\`, with `video.mp4` in it (or in a named stream's subfolder) and `audio.wav` beside it; the app uses the newest take that is complete (see When a take counts). **Finish** sends the host the clip id, the job, the take folder and the lower third's two lines, with personal info hidden when that setting is on. The host (`app/src-tauri/src/clips/ffmpeg.rs`) resolves the take inside the clips folder, writes the lines to `clips\text\`, takes the font from a fixed list in Windows' Fonts folder, and builds the FFmpeg command, which trims each take to the moment, draws the reason in a lower third and keeps the take's sound; a take without `audio.wav` is not finished. FFmpeg is looked up before anything is written, so a missing FFmpeg leaves no file behind. No argument may name a protocol or a file-reading filter. FFmpeg writes a new `.part.mp4` file beside the clip, renamed over `<clip id>.mp4` only after it exits cleanly with a non-empty file and removed otherwise, so a failed render never stands as a clip and never replaces a good one; the page lists only non-empty final files. The result is `%APPDATA%\BotMatchStats\clips\<clip id>.mp4`. **Make a reel** joins rendered clips into `clips\reels\`.

## Locking the camera

CS2 1.41.6.2 (build 23296257, 2026-05-18) changed how the demo camera answers console commands. In [advancedfx issue #1172](https://github.com/advancedfx/advancedfx/issues/1172) (2026-05-22, HLAE 2.190.1), a single `spec_player <slot>` sent from a cfg left the camera on the demo's default player whatever the slot, `spec_lock_to_accountid` did the same, and `spec_next` stepped through free-camera stops; `spec_mode 1` gave the in-eye view and `spec_mode 4` the free camera. HLAE's author answered with the `mirv_script_spec_lock` snippet, which the [HLAE wiki](https://github.com/advancedfx/advancedfx/wiki/Source2%3ACommands#script-snippet-commands-experimental) describes as "Locks spec_player on a specfic player": it sends `spec_player <controller entity index>` on every frame (`misc/mirv-script/src/snippets/mirv_script_spec_lock.ts`), used with `spec_mode 1`. The reporter confirmed that solved it and closed the issue (2026-05-24). No HLAE release since (2.190.2 to 2.192.10, 2026-10-24) adds a native spectate command, and HLAE's source has none, so this snippet's method is the one HLAE supports.

The director does the same from inside its own script: from the moment it lands before a clip until the clip ends, it sends `spec_player <controller entity index>` every frame. The index is the one `mirv_script_spec_lock list` prints, the controller's entity index, which the director finds by SteamID64. For first person it sends, while the mode does not read in-eye, `spec_mode 2` for 30 frames, then `spec_mode 1` for 30, and so on in turn. 2 is in-eye in CS2's `ObserverMode_t` (0 none, 1 fixed, 2 in-eye, 3 chase, 4 roaming, in CounterStrikeSharp's generated schema), and HLAE's own `mirv_script_view` snippet passes `getObserverMode()` values to `spec_mode` and reads 2 as in-eye. 1 is the value #1172 found gives in-eye on 1.41.6.2, where `spec_mode 2` was not tried. Whichever command works, the director records only when the local pawn's `getObserverMode()` reads 2 and the observed player is the clip's player, on a frame before the start tick.

Verified: that the director sends these commands in this order and records only on that readback, against a stand-in for HLAE's script API (`director.test.ts`). Not verified, because nobody has run it in CS2: on today's build (1.41.9.2), that holding `spec_player` every frame keeps the camera on the player, which `spec_mode` value gives the in-eye view, and that `getObserverMode()` then reads 2. If the readback never confirms, every clip ends with `camera_late` or `camera_mode_unknown` and no take counts: the render fails closed, and the first supervised render will show which part failed.

## Keeping operations apart

Every clips command runs in the one app process, and each that writes runs under one process-wide mutex (`launch::guard`): a scan, saving a plan, a launch with its record and process ids, the settling of launches, a finish, a reel and the part-file sweep never interleave. A finish holds it while FFmpeg runs, so a scan started then waits for the finish to end.

The same guard holds the clips folder's OS lock: `clips\clips.lock`, open with no sharing. A second instance of the app cannot open it and says so. The system closes the handle when the process ends, however it ends, so a lock never outlives its owner and nothing ever has to decide that a lock is stale. After a launch, a watcher thread keeps the OS lock. It holds HLAE's process handle from the start and waits for that process to exit, then for no cs2.exe to run; then it takes the guard, settles that launch (reads `console.log` and publishes its result), and only then lets the OS lock go, so no other instance of the app can start a CS2 session that replaces the log before it is read. It only waits and reads the process list; it never stops a process.

Files the host publishes about a launch (its record, process ids and result) are written to a temporary file and renamed into place by a rename that fails when the name exists, so a reader sees a whole file or none, and nothing is ever replaced.

## When a take counts

HLAE's script cannot write files (its mirv-script `fs.d.ts` only reads folders), so the director's record is CS2's console log. Three things make that record trustworthy:

- **A nonce per launch.** Every launch gets a fresh 128-bit random nonce, written only into that launch's copy of the director. A demo's chat and player names were recorded before the nonce existed, so they cannot hold it, and a line from an earlier launch holds an older one. The host reads only lines that start with `[cs2stats] END ` and carry this launch's nonce: `[cs2stats] END <clip id> nonce=<nonce> why=<why> tick=<tick>`.
- **Read once, after the processes exit.** A launch is settled when HLAE's own process (its id and creation time) has exited and no cs2.exe runs. Nothing here can confirm that HLAE is the parent the system records for the cs2.exe its loader starts, so "no cs2.exe at all" stands in for "its CS2 has exited". The host then reads the whole of `console.log`, streamed one line at a time in constant memory with no limit on its size, and publishes what it found as `launches\<nonce>.result.json`. Reading from the start is always right: with the nonce, a line from another session cannot count, however the log was truncated, replaced or regrown. A result that does not read (a file damaged by something other than the app) marks only that launch as damaged, and its takes do not count; the scan goes on. A launch with no recorded HLAE process settles as damaged too, never as "not started": the app may have stopped between starting HLAE and recording it, and a start that failed says so in its result at once.
- **A take belongs to one launch:** the launch with the highest sequence number whose record does not list the take. Sequence numbers are assigned under the guard; nothing orders launches by the clock, so a clock moved back changes nothing. A launch waits for the one before it, so that is the launch that made the take.

A take is recorded, and Finish accepts it, when its launch is settled, that launch's lines include `END <clip> nonce=<nonce> why=end_tick`, and the take holds a non-empty `video.mp4` and the `audio.wav` the job asked for (the setup always runs `mirv_streams record startMovieWav 1`). No timing check is needed: when a process exits, the system closes its files, and the host reads them through the same system cache. For each clip the page takes the newest take that passes, so a newer take that failed does not hide an older one that worked.

What this cannot detect:

- A launch whose lines never reached the log: CS2 crashed, or was closed before the director logged the clip's `END`. Its takes stay unrecorded; render those moments again.
- A clip the director stopped early or skipped (`why=demo_end`, `camera_lost`, `camera_late`, `camera_mode_unknown`, `no_player`, `seek_failed` or `error`) does not count; render it again.
- Whether 0.5 s after a death is still before CS2 moves the demo camera. Clips end there (step 1); if CS2 switches at the death tick itself, a moment where the player dies inside the clip ends with `camera_lost` and does not count, and the tail must go to 0. The first supervised render will show which.
- Whether CS2 writes `mirv.message` lines at the start of a console.log line. The parser requires it, so that chat cannot forge a line; if CS2 prefixes its lines, every take stays unrecorded and the first supervised render will show it.

FFmpeg's part files (`.*.part.mp4`) that a crashed finish leaves are removed at app start and with every scan, under the guard, so never while a finish writes one.

## What is checked and what is not

Checked without the game:

- Moment scoring has known-answer tests on hand-built rounds (`moments.test.ts`).
- The launch (`clips/launch.rs`, `clips/mod.rs`) has Rust tests: a finish and a scan's sweep driven through the guard, where the sweep waits and never removes the finish's part file; a lock held by another process, which the app refuses while that process (started by the test, and ended by its own handle) holds it, then takes once it has ended; a clock moved backwards; settling earlier launches before a new one, and waiting while one runs; a relaunch after a failed run; chat lines and old or guessed nonces; a log truncated and regrown with the END line early, and an END line past 64 MiB; a partial result file; a launch settled only after its processes exit, and only once; a watcher that settles its launch before the lock goes; a launch whose process ids cannot be published, which keeps HLAE and the lock and settles as damaged whatever its log says; a start that fails; saving a plan, which waits for the guard and refuses a plan whose review value changed; a take behind a junction, neither listed nor finished; and a missing FFmpeg, which refuses before any file is written.
- A malformed demo is an error, never a panic: truncated, overlong and 64-bit-overflowing varints, lengths past the end and of `u64::MAX`, and every truncation and many single-byte changes of a good file-info frame (`clips/job.rs`).
- The job (`clips/job.rs`) has Rust tests: the exact command, the folder and cfg, grouping by demo, refusals by name (a start before the director's lead among them), a junction named like a demo, unique ids, the paired write, and a review value that ignores the job's id and changes with the HLAE or a clip's ticks. The launch's rebuild refuses a tampered plan (an extra game flag, another program, another cfg line) and replaces an edited director (`clips/mod.rs`). Finishing and reels refuse links and paths outside the clips folder.
- The director runs in `director.test.ts` against a stand-in for HLAE's script API, which plays two demos tick by tick and stands in for the cvar API. That checks its order of work, the commands it sends and that `demo_ui_mode` is put back before `quit`, and the camera rules: a lock that comes after the start seeks back, a camera that never locks skips with `camera_late`, a demo in chase mode is forced to first person before recording, `spec_mode 1` is tried when `spec_mode 2` does not give in-eye, `spec_player` is sent on every recorded frame, an HLAE without `getObserverMode` skips, and leaving first person while recording stops with `camera_lost`. It does not check how CS2 answers.
- The FFmpeg templates run on synthetic takes from `testsrc2` in a Rust test (`clips/ffmpeg.rs`). It checks durations, stream shapes, where the lower third is drawn and that it is absent before its fade-in, and the reel's length. It skips, saying why, where FFmpeg or a font is missing, as on CI's runners.

Not checked, because nobody has run any of this inside CS2:

- that HLAE 2.192.x starts this game build with these flags, and that `+exec` runs the cfg after HLAE's commands exist;
- that holding `spec_player <controller index>` every frame keeps the camera on the player on CS2 1.41.9.2, which `spec_mode` value gives the in-eye view there, and that the local pawn's `getObserverMode()` then reads 2 (see Locking the camera);
- that the extractor's ticks (demoparser2) equal what `demo_gototick` and `mirv.getDemoTick()` use. povforge assumes so;
- whether CS2 saves `demo_ui_mode` to the user's config at all, and whether HLAE's cvar API reaches it (the director puts it back either way, but a crash or a closed game before the director's last step would leave it at 0);
- local `tv_autorecord` demos and HLTV demos.

## Threat model

The host's checks (`app/src-tauri/src/clips/`) defend against inputs the app does not control: the web view's requests, a stale or edited `plan.json` or `director.js`, a link or junction left inside the clips folder, and a file disguised as a take. Against those:

- the web view sends typed requests, and the host builds every command and path;
- saving and launching build the job again and refuse a plan that differs from the saved one or from the one the user reviewed;
- every path read or written is resolved, links included, and checked to be inside its folder; a take, a lower-third file or an output that is itself a link is refused, and so is a file read through a link or junction anywhere below the clips folder, and an output with another hard link, which FFmpeg's overwrite would write through. The scan applies the same checks, so it lists only what finishing would read;
- FFmpeg opens each input with a fixed demuxer (`-f mp4` or `-f wav`) and only through the file protocol (`-protocol_whitelist file`), so a playlist or concat list hidden inside a video cannot name other files; the reel uses the concat filter, not the concat demuxer, so `-safe` does not apply;
- files the host writes go to a new temporary name created exclusively and are then renamed into place, so nothing already at that path is written into.

Out of scope: another process running as the same user that can already write to `%APPDATA%\BotMatchStats\clips` or to CS2's replays folder. That process can read anything the user can, so racing a check against it protects nothing. This is the same ruling as the packs folder (#41). For the same reason CS2's replays folder may be a junction: the checks resolve it before comparing, and a user can legitimately move it with one. Inside the clips folder the app never needs one, so a junction there is refused.

## Screenshots of states that need CS2

No agent may start CS2, so the states a render puts the page in come from a stand-in clips host, `app/src/clips/mock.ts`. `vite dev` and `pnpm capture` load it with `?clips=waiting` (a launch's CS2 still runs), `?clips=ready` (the dialog's plan arrives at once) or `?clips=held` (the plan never arrives, so Save and Launch stay off), for example `/?clips=held#/clips`. It reports every demo on disk and every tool found, and refuses to save, launch or run FFmpeg. `clipsHost` imports it only when `import.meta.env.DEV` is set, so the release build drops it: after `pnpm build`, neither its marker string `cs2stats-mock-clips-host` nor `mockClipsHost` appears anywhere in `app/dist`. With `CS2_VALVE_MATCHES` pointing at a folder of extracted Valve matches, the moments are real and only the host is stood in.

## The first supervised render

The user runs this, at the machine, with nothing else using CS2.

1. Download HLAE from https://github.com/advancedfx/advancedfx/releases, unpack it to a folder of your own (`D:\Tools\HLAE`, say), and leave its `x64` folder beside `HLAE.exe`.
2. Install FFmpeg if `ffmpeg -version` fails in a terminal (`winget install Gyan.FFmpeg`).
3. Import a recent Valve match in Data & settings, so its demo is still in CS2's replays folder.
4. Close CS2. Open Clips. The dots for CS2, HLAE and FFmpeg should all be green. If HLAE's is not, its path goes in the Render dialog.
5. Choose one short "Ready to render" moment and press Render. Read the command and the files it lists, then press **Launch CS2 with -insecure**.
6. Leave the game alone. CS2 opens, loads the demo, records and quits. If it does not quit within a few minutes of the clip's length, close it yourself.
7. Back in Clips, wait until the page no longer says it is waiting for CS2 to close. The moment should read "Recorded". Choose it and press Finish.
8. Check `game\csgo\console.log` for the `[cs2stats]` lines and the finished MP4 for the right player and the right kills. Report the HLAE version, the CS2 build and anything that went wrong on issue #11.
